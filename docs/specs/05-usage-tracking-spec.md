# Usage Tracking & Cost Calculation Specification

## 1. Overview

This document specifies how the gateway tracks usage of proxied requests and calculates costs
based on token consumption. All data is persisted to a SQLite database for later analysis via
the admin dashboard or external tools.

---

## 2. Data Model: Usage Records

Each proxied request generates one `UsageRecord` entry in the SQLite database.

### Schema (SQL)

```sql
CREATE TABLE IF NOT EXISTS usage_records (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp       TEXT    NOT NULL,                    -- ISO 8601 UTC: "2025-01-15T14:30:00Z"
    api_key_id      TEXT    NOT NULL,                    -- e.g., "user-001"; never stores raw key
    model           TEXT    NOT NULL,                    -- resolved (real) model name after aliasing
    backend_url     TEXT    NOT NULL,                    -- URL of the backend that served this request
    prompt_tokens   INTEGER DEFAULT 0,                   -- from Ollama's prompt_eval_count field
    completion_tokens INTEGER DEFAULT 0,                 -- from Ollama's eval_count field
    duration_ms     INTEGER NOT NULL,                    -- total request time: first byte in → last byte out
    cost_usd        REAL    DEFAULT 0.0                  -- calculated cost for this single request
);

CREATE INDEX IF NOT EXISTS idx_usage_timestamp ON usage_records(timestamp);
CREATE INDEX IF NOT EXISTS idx_usage_api_key_id ON usage_records(api_key_id);
CREATE INDEX IF NOT EXISTS idx_usage_model ON usage_records(model);
```

### Go Struct Mapping

```go
type UsageRecord struct {
    ID              int64   `db:"id" json:"-"`
    Timestamp       string  `db:"timestamp" json:"timestamp"`            // ISO 8601 UTC
    APIKeyID        string  `db:"api_key_id" json:"api_key_id"`          // Hashed ID, never raw key
    Model           string  `db:"model" json:"model"`                    // Resolved model name (post-alias)
    BackendURL      string  `db:"backend_url" json:"backend_url"`        // e.g., "http://localhost:11434"
    PromptTokens    int     `db:"prompt_tokens" json:"prompt_tokens"`    // prompt_eval_count from Ollama
    CompletionTokens int    `db:"completion_tokens" json:"completion_tokens"`  // eval_count from Ollama
    DurationMS      int     `db:"duration_ms" json:"duration_ms"`        // measured by gateway proxy handler
    CostUSD         float64 `db:"cost_usd" json:"cost_usd"`              // calculated cost for this request
}
```

## 3. Token Count Extraction

### Non-Streaming Responses (`stream: false`)

Ollama returns a single JSON object with these fields in the final response:

```json
{
  "prompt_eval_count": 26, // number of tokens in the prompt
  "eval_count": 150 // number of tokens generated by the model
}
```

The gateway's `ModifyResponse` handler parses this JSON and extracts both values. These are stored
in request-scoped context for the async usage logger to pick up after the response is sent to client.

### Streaming Responses (`stream: true`)

Ollama sends newline-delimited JSON objects, each a partial result. The final chunk contains token counts:

```jsonl
{"response":"The","done":false}
{"response":" sky","done":false}
{"response":" is blue.","done":true,"prompt_eval_count":5,"eval_count":10,...}
```

The gateway wraps the client's `io.Writer` with a streaming capture writer (detailed in the API proxy spec) that:

- Buffers partial lines until complete JSON objects are received.
- Extracts `prompt_eval_count` from any chunk where it appears and is non-zero.
- Tracks the maximum/last seen value of `eval_count` across all chunks (it accumulates).

### Fallback Behavior for Token Counts

If token counts cannot be extracted from a response (e.g., malformed JSON, unexpected format):

| Field            | Default Value When Unavailable | Reasonable?                                            |
| ---------------- | ------------------------------ | ------------------------------------------------------ |
| PromptTokens     | 0                              | Conservative — undercounts cost. Better than guessing. |
| CompletionTokens | 0                              | Same rationale.                                        |
| CostUSD          | 0.0 (calculated from above)    | Derived value, so also defaults to 0 if inputs are 0.  |

### Non-Token-Based Endpoints

For endpoints that don't produce token counts in their responses:

- `/api/embed` — Returns embeddings only; no `prompt_eval_count`/`eval_count`. Tokens logged as 0.
- `/api/tags`, `/api/ps`, `/api/version` — Metadata-only requests. Not proxied through the usage logging path (they bypass model resolution since they don't take a single model). However, if they are routed to backends via default round-robin, they will still be logged with token counts = 0 and duration measured normally.

## 4. Duration Measurement

### What Is Measured

Duration is measured from the gateway's perspective:

- **Start**: When the proxy handler begins processing (after auth + rate limit checks pass), immediately before forwarding to backend.
- **End**: When the last byte of the response has been written back to the client.

This includes network round-trip time to/from backend and any serialization overhead within the gateway itself, but excludes time spent in auth/rate-limiting middleware (those are measured separately if needed).

### Implementation Approach

```go
start := time.Now()

// ... proxy handler runs ReverseProxy.ServeHTTP which blocks until response complete ...

durationMS := int(time.Since(start).Milliseconds())
usageRecord.DurationMS = durationMS
```

For streaming responses, `ReverseProxy` with immediate flushing ensures this measures the full stream duration — from first byte received to last byte sent.

## 5. Cost Calculation

### Pricing Configuration

Pricing is configured per model (with global defaults) in the YAML config:

```yaml
pricing:
  default_input_per_1m_tokens: 0.0 # USD per 1M input tokens; applies to any unpriced model
  default_output_per_1m_tokens: 0.0 # USD per 1M output tokens
  models:
    "llama3.2:latest":
      input_cost_per_1m_tokens: 0.0
      output_cost_per_1m_tokens: 0.0
    "gemma2:latest":
      input_cost_per_1m_tokens: 0.5
      output_cost_per_1m_tokens: 1.5
```

### Cost Formula

For a single request with `P` prompt tokens and `C` completion tokens, using model-specific or default pricing:

$$
\text{Cost} = \frac{P}{1{,}000{,}000} \times R_{\text{in}} + \frac{C}{1{,}000{,}000} \times R_{\text{out}}
$$

Where:

- $R_{\text{in}}$ is the input cost per 1M tokens (model-specific or default).
- $R_{\text{out}}$ is the output cost per 1M tokens (model-specific or default).

### Example Calculation

Given `llama3.2:latest` with `input_cost_per_1m_tokens = 0.5`, `output_cost_per_1m_tokens = 1.5`:

- Prompt tokens: 500
- Completion tokens: 200

$$
\text{Cost} = \frac{500}{1{,}000{,}000} \times 0.5 + \frac{200}{1{,}000{,}000} \times 1.5 = 0.00025 + 0.0003 = \$0.00055
$$

### Go Implementation

```go
type PricingConfig struct {
    DefaultInputPer1M   float64            `yaml:"default_input_per_1m_tokens" json:"-"`
    DefaultOutputPer1M  float64            `yaml:"default_output_per_1m_tokens" json:"-"`
    ModelPricing        map[string]ModelPricing `yaml:"models" json:"-"`
}

type ModelPricing struct {
    InputCostPer1M  float64 `yaml:"input_cost_per_1m_tokens" json:"-"`
    OutputCostPer1M float64 `yaml:"output_cost_per_1m_tokens" json:"-"`
}

func (pc *PricingConfig) CalculateCost(model string, promptTokens, completionTokens int) float64 {
    pricing := pc.ModelPricing[model]  // Returns zero-value if not found → defaults used below

    inputRate := pricing.InputCostPer1M
    outputRate := pricing.OutputCostPer1M

    // Fall back to global defaults for any unset (zero) rates
    if inputRate == 0 {
        inputRate = pc.DefaultInputPer1M
    }
    if outputRate == 0 {
        outputRate = pc.DefaultOutputPer1M
    }

    cost := float64(promptTokens)/1_000_000.0 * inputRate +
            float64(completionTokens)/1_000_000.0 * outputRate

    return math.Round(cost*1e8) / 1e8  // Round to nearest $0.00000001 (avoids floating-point noise in sums)
}
```

## 6. Persistence & Storage Strategy

### SQLite Database

- File-based SQLite database at the path specified by `database.path` config option
  (default: `.data/gateway.db`).
- Created automatically on first startup if it doesn't exist.
- Schema initialized via embedded SQL migration scripts (`internal/db/migrations/001_init.sql`)
  applied using Go's `database/sql` package with a lightweight migration approach (check
  for table existence before creating — no external migrate tool dependency).

### Async Logging Architecture

To avoid blocking the proxy request path, usage records are written asynchronously:

````go
type UsageLogger struct {
    db     *sql.DB
    ch     chan UsageRecord        // Buffered channel; capacity configurable (default 1024)
    quit   chan struct{}
}

// Proxy handler calls this after response is sent to client — non-blocking if buffer has space:
func (ul *UsageLogger) Log(record UsageRecord) {
    select {
    case ul.ch <- record:
        // queued successfully
    default:
        // Channel full! Drop the oldest entry and queue new one, or log warning.
        log.Warn("usage logger channel full; dropping oldest record")
        select {
        case <-ul.ch:           // discard oldest
            ul.ch <- record      // try again (will still be non-blocking if buffer freed)
        default:
            return              // give up entirely to avoid blocking proxy path
        }
    }
}

// Background goroutine reads from channel and writes batch inserts every 1s or 50 records:
func (ul *UsageLogger) run() {
    ticker := time.NewTicker(time.Second)
    defer ticker.Stop()

    var batch []UsageRecord
    flush := func() {
        if len(batch) == 0 { return }
        ul.batchInsert(batch)
        batch = batch[:0]
    }

    for {
        select {
        case rec := <-ul.ch:
            batch = append(batch, rec)
            if len(batch) >= 50 {
                flush()
            }
        case <-ticker.C:
            flush()
        case <-ul.quit:
            flush()   // final drain on shutdown
            return
        }
    }
}

## 7. Dashboard Overview Aggregation Windows

The dashboard Overview page supports windowed aggregate analytics via the usage store APIs:

- `OverviewSummary(opts OverviewOptions)`
- `ModelCostBreakdown(limit int, opts OverviewOptions)`

`OverviewOptions` accepts optional RFC3339 bounds:

```go
type OverviewOptions struct {
    Start string
    End   string
}
````

### Window semantics

- `all` window: no bounds applied (all-time totals).
- `24h` window: `Start=now-24h`, `End=now`.
- `7d` window: `Start=now-7d`, `End=now`.

The SQL filters are applied as:

```sql
WHERE timestamp >= ? AND timestamp <= ?
```

when bounds are provided; otherwise no `WHERE` clause is added for timestamp.

### Dashboard refresh behavior

- `/admin/overview` renders full page content.
- `/admin/overview/partial` renders Overview fragment content used by HTMX polling every 10 seconds.
- Polling is paused while the browser tab is hidden and resumes with an immediate refresh when visible again.

````

### Batch Insert SQL

Uses a single transaction with multiple `INSERT` statements for efficiency:

```sql
BEGIN;
INSERT INTO usage_records (timestamp, api_key_id, model, backend_url, prompt_tokens, completion_tokens, duration_ms, cost_usd) VALUES (?, ?, ?, ?, ?, ?, ?, ?);
-- ... more rows in same statement batch ...
COMMIT;
````

### Graceful Shutdown Handling

On SIGTERM/SIGINT:

1. Stop accepting new HTTP connections (graceful server shutdown with 30s timeout).
2. Wait for all active proxy requests to complete.
3. Signal the usage logger's `quit` channel — it performs a final flush of any buffered records.
4. Close DB connection and exit.

This ensures no in-flight or queued usage data is lost during restarts.

## 7. Query Examples (for Dashboard)

### Total Requests & Token Usage in Last 24 Hours

```sql
SELECT
    COUNT(*) AS total_requests,
    SUM(prompt_tokens) AS total_prompt_tokens,
    SUM(completion_tokens) AS total_completion_tokens,
    ROUND(SUM(cost_usd), 6) AS total_cost_usd
FROM usage_records
WHERE timestamp >= datetime('now', '-24 hours');
```

### Daily Breakdown for Last 7 Days (for chart data)

```sql
SELECT
    date(timestamp) AS day,
    COUNT(*) AS requests,
    SUM(prompt_tokens) AS prompt_tokens,
    SUM(completion_tokens) AS completion_tokens,
    ROUND(SUM(cost_usd), 6) AS cost_usd
FROM usage_records
WHERE timestamp >= datetime('now', '-7 days')
GROUP BY date(timestamp)
ORDER BY day DESC;
```

### Top Models by Token Usage (Last 24h)

```sql
SELECT
    model,
    COUNT(*) AS requests,
    SUM(prompt_tokens + completion_tokens) AS total_tokens,
    ROUND(SUM(cost_usd), 6) AS cost_usd
FROM usage_records
WHERE timestamp >= datetime('now', '-24 hours')
GROUP BY model
ORDER BY total_tokens DESC
LIMIT 10;
```

### Recent Requests (Paginated Table for Dashboard)

```sql
SELECT id, timestamp, api_key_id, model, backend_url, prompt_tokens, completion_tokens, duration_ms, cost_usd
FROM usage_records
WHERE (:api_key_filter IS NULL OR api_key_id = :api_key_filter)
  AND (:model_filter IS NULL OR model = :model_filter)
ORDER BY timestamp DESC
LIMIT :limit OFFSET :offset;
```

## 8. Edge Cases & Validation Rules

| Rule                                                                      | Behavior                                                                                                                                                                                     |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Token counts are negative or absurdly large (> 1M per field)              | Clamped to reasonable maximum (e.g., 500,000); logged as a warning. Prevents cost calculation anomalies from malformed backend responses.                                                    |
| Duration is 0ms (sub-millisecond request completed before timer resolved) | Stored as-is; acceptable for very fast endpoints like `/api/version`.                                                                                                                        |
| Database write fails during batch insert                                  | Error is logged but does not affect the client response — usage data loss is non-critical and will be visible in logs. Channel buffer may fill up, triggering drop behavior described above. |
| Model has no pricing entry and global defaults are 0                      | Cost = $0.0 for that request; appears as free in analytics. Operator should set meaningful defaults or per-model rates.                                                                      |
| Database file is deleted while gateway is running                         | Next batch insert fails silently (logged). Gateway continues operating — new DB will be created on next startup with schema re-applied automatically if path still writable.                 |
